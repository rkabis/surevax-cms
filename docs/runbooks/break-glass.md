# Emergency Tenant-Admin Account Recovery Runbook

> **Status: MAINTAINED PHASE-1 REPOSITORY CONTROL.** This runbook covers the
> repository-native, one-time account-recovery lease. It does not create an
> emergency user, reveal or reset a password, grant a role, bypass tenant RLS,
> or authorize cross-tenant access. The repository verifies two authenticated,
> distinct, current TenantAdmin approval identities; the incident declaration
> and operator authorization remain owner-controlled evidence.

## Purpose and boundary

Use this mechanism only when an existing, active TenantAdmin cannot log in
during a declared incident and the ordinary password-reset path cannot restore
access quickly enough. Its only permitted purpose is
`restore_tenant_admin_login`.

The lease is:

- bound to one tenant, one existing TenantAdmin, and one incident;
- linked to one short-lived approval request approved through authenticated
  sessions by two distinct current TenantAdmins other than the requester and
  target;
- time-bounded;
- represented by a random token whose hash, not plaintext, is stored;
- consumable once and rejected after use, expiry, or revocation; and
- audited on grant, execution, and revocation.

This mechanism is not the clinical cross-branch chart-reveal feature. It must
not be used to inspect a patient chart, broaden branch access, create an admin,
change a role, or obtain platform-admin access.

## Roles

| Role                      | Responsibility                                                                                                                            |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Incident Commander        | Declares the incident, fixes the tenant and target user in scope, and owns the recovery decision.                                         |
| Requesting operator       | Creates the repository approval request using their own active tenant-user display ID; cannot approve it.                                 |
| Two TenantAdmin approvers | Approve the exact request through separate authenticated sessions; neither may be the requester or target.                                |
| Executing operator        | Mints/executes the lease, protects the one-time token, and records non-secret evidence. The operator must not be the only external owner. |
| Reviewer                  | Reconciles the approval, grant, execution or revocation, login recovery, and account activity before closure.                             |

The repository approval display ID is the authorization reference used by the
grant command. The two votes are bound to authenticated user IDs and checked
again at grant time for active TenantAdmin membership. External incident and
operator approvals remain durable owner evidence. Never paste PHI, passwords,
tokens, request bodies, or patient details into either evidence channel.

## Preconditions

- [ ] A declared incident ID exists.
- [ ] The exact tenant slug and target user display ID are recorded.
- [ ] The target is an existing active TenantAdmin in that tenant.
- [ ] A repository approval request exists for the exact incident, tenant,
      target, and fixed purpose.
- [ ] Two distinct current TenantAdmins other than the requester and target
      approved that request through authenticated sessions.
- [ ] Ordinary password reset has been attempted or documented as unavailable.
- [ ] The executing operator has a protected terminal and an approved database
      connection path. Shell history, screen sharing, and session recording are
      disabled for the token-handling step.
- [ ] A reviewer and an out-of-band contact path are available.

Stop if any item is false. Never substitute the Postgres master role as the
application runtime credential.

## Repository command

Run the maintained CLI from the repository root through the backend package.
The activation token must be generated by the operator, contain at least 32
characters, and arrive on standard input from an approved protected secret
source. The CLI rejects an interactive terminal so it cannot echo the token.

The supported lifecycle is request → authenticated votes → grant → execute or
revoke:

```bash
# Create a one-hour repository approval request. This prints only APR_ evidence.
pnpm --filter @surevax/backend incident-access -- request \
  --tenant <TENANT_SLUG> \
  --requester <REQUESTER_USR_DISPLAY_ID> \
  --user <TARGET_USR_DISPLAY_ID> \
  --incident <OPAQUE_INCIDENT_ID>

# Two different current TenantAdmins approve the returned APR_ request through
# PATCH /api/admin/approvals/<APR_DISPLAY_ID>/approve using their own sessions.

# Generate into an unexported shell variable in the protected terminal. The
# command, but not the generated value, may appear in shell history.
SUREVAX_RECOVERY_TOKEN="$(openssl rand -hex 32)"

printf '%s' "$SUREVAX_RECOVERY_TOKEN" | \
  pnpm --filter @surevax/backend incident-access -- grant \
    --tenant <TENANT_SLUG> \
    --user <USR_DISPLAY_ID> \
    --incident <INCIDENT_ID> \
    --approval <APR_DISPLAY_ID> \
    --duration <5_TO_30_MINUTES>

printf '%s' "$SUREVAX_RECOVERY_TOKEN" | \
  pnpm --filter @surevax/backend incident-access -- execute \
    --tenant <TENANT_SLUG> \
    --grant <EAG_DISPLAY_ID>

pnpm --filter @surevax/backend incident-access -- revoke \
  --tenant <TENANT_SLUG> \
  --grant <EAG_DISPLAY_ID>

# Clear the in-memory plaintext immediately after execute or revoke. If a
# different operator executes, transfer it first through the approved secret
# channel, never chat/ticket/email.
unset SUREVAX_RECOVERY_TOKEN
```

Required grant inputs are the tenant slug, target user display ID, incident ID,
the approved repository `APR_` display ID, and a 5–30 minute duration. The
purpose is fixed by the tool and cannot be overridden. Grant fails unless the
approval is unexpired, matches the tenant/incident/target/purpose, has quorum,
and still resolves to two distinct active TenantAdmins other than the target.
The grant command prints only the grant display ID and expiry; it never prints
or stores the plaintext token. Retain the operator-generated token only in the
approved secret-transfer channel until execution or revocation.

Execution supplies the tenant, grant display ID, and token. The grant itself
binds the target, incident, approvals, and purpose. The tool atomically rejects
a token that is unknown, mismatched, expired, revoked, or already used.
Successful execution clears only the existing account's login lockout counters
and revokes its active refresh tokens. It does not change the user's tenant,
role, primary branch, password, MFA secret, `can_login`, status, or permissions.

Revocation must identify the same tenant and grant. Use it immediately if the
incident is cancelled, the token may have been exposed, the target changes, or
the lease is no longer needed. Revocation is not a substitute for token-family
revocation after suspected credential compromise.

## Execution procedure

### 1. Request and approve

1. Resolve the requester and target by public user display ID; do not use a bigint ID in the
   incident record or CLI interface.
2. Create the repository request and record the returned `APR_` display ID.
3. Have two eligible TenantAdmins approve it from separate authenticated
   sessions. Direct database, duplicate, requester, target, cross-tenant, and
   non-TenantAdmin votes fail closed.

### 2. Grant

1. Reconcile the approval detail and decision history to the incident.
2. Grant the shortest practical lease. Thirty minutes is the operational
   ceiling unless a shorter repository-enforced maximum applies.
3. Record only the returned grant display ID, created/expiry timestamps, tenant,
   target user display ID, purpose, incident ID, and approval request ID.
4. Keep the operator-generated plaintext token only in the approved secret
   channel until execution; the CLI never returns it.

### 3. Execute

1. Reconfirm incident state and target immediately before execution.
2. Execute once. A retry after success must fail as replayed access.
3. Confirm the output identifies the grant and target but contains no token,
   password, credential, or PHI.
4. Have the TenantAdmin authenticate through the normal application flow using
   their existing credential or complete the normal password-reset flow.
5. Do not perform clinical work under the executing operator's identity.

### 4. Revoke or close

Revoke an unused lease as soon as recovery is no longer required. After a
successful execution, verify the consumed timestamp and proceed to review; an
already-consumed lease cannot be made reusable.

If account compromise is suspected, also revoke the affected user's refresh
token family and rotate the signing secret that was exposed:

- rotate `JWT_ACCESS_SECRET` to invalidate access tokens;
- rotate `JWT_REFRESH_SECRET` and revoke server-side refresh-token families to
  invalidate refresh sessions; and
- do not rely on rotating the legacy `JWT_SECRET`, which is not used to sign
  current access or refresh tokens.

Secret rotation is an external Railway action. Record the variable version or
change reference, never the secret value.

## Verification and negative drills

Before pilot admission, and after material changes, preserve evidence that:

| Drill                        | Expected result                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------- |
| Wrong tenant or wrong target | Execution is rejected and no account state changes.                                   |
| Non-TenantAdmin target       | Grant or execution is rejected.                                                       |
| Missing/invented approval    | Grant is rejected.                                                                    |
| Invalid approval identity    | Duplicate, requester, target, or non-TenantAdmin votes are rejected.                  |
| Revoked approver role        | Grant is rejected even if the request previously reached quorum.                      |
| Expired token                | Execution is rejected and the lease remains unusable.                                 |
| Revoked token                | Execution is rejected.                                                                |
| Replayed token               | The first valid execution may succeed; every later execution is rejected.             |
| Scope inspection             | Tenant, role, branch, password, MFA, and permissions are unchanged.                   |
| Audit reconciliation         | Grant, execute or revoke evidence matches the incident and contains no secret or PHI. |

## Prohibited actions

- Creating a one-time SuperAdmin or sharing a generic credential.
- Printing, logging, persisting, or ticketing the plaintext token.
- Passing a token through an observable command-line argument when the CLI
  provides a protected prompt or standard-input path.
- Using a platform-admin or database-owner context to widen tenant scope.
- Changing the target's role, tenant, branch, password, or MFA configuration.
- Reusing clinical cross-branch access grants for account recovery.
- Disabling RLS, audit triggers, alert delivery, or token replay checks.
- Treating successful account recovery as incident closure.
